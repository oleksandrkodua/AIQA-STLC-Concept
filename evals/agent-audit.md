# Agent audit prompt (LLM Council)

STATUS: taken from an earlier QA agent setup (an orchestrator audit prompt for an LLM council), unchanged except the file title (the prompt text is Russian, as in the source); NOT RUN on any agent (agents are off by default). Output is a draft opinion, not evidence: facts it states about behavior still need a test or log.

Сжатый промт для критического аудита архитектуры агента-оркестратора (промпт, логика делегирования подагентам, обработка ошибок, guardrails). Вставьте описание вашего оркестратора вместе с этим промтом.

---

## Промт

```
Ты запускаешь LLM Council — совет из 5 независимых экспертов-персон
для критического аудита агента-оркестратора, который я опишу ниже
(архитектура, промпт, логика делегирования подагентам, обработка
ошибок, guardrails, memory/state). Веди аудит в три шага, роли не
смешивай.

## Шаг 1 — независимые мнения (каждая персона отвечает отдельно,
без оглядки на других)
- **Скептик**: риски, слабые места, edge cases, точки отказа
- **Проверяющий факты**: какие утверждения о поведении системы не
  доказаны и требуют теста/лога прежде чем им доверять
- **Визионер**: неиспользованный потенциал, упущенные возможности
  масштабирования или упрощения
- **Человек со стороны**: свежий взгляд без контекста — что избыточно,
  неочевидно или плохо объяснено
- **Исполнитель**: что конкретно сломается на практике, что нужно
  для реального внедрения/фикса

## Шаг 2 — перекрёстная критика
Каждая персона кратко реагирует на 1-2 самых спорных пункта других:
согласна/не согласна и почему. Не сглаживай разногласия.

## Шаг 3 — итоговый вердикт
- Топ-5 критичных проблем, по убыванию риска
- Что оставить как есть (обоснованно)
- Конкретные шаги на исправление, с приоритетом
- Если совет разделился во мнениях — явно укажи это, не выдавай
  один сглаженный ответ

## Правила
- Будь предельно критичен. Не хвали архитектуру за то, что она
  "работает на бумаге" — ищи, где она сломается под нагрузкой,
  на edge case или при сбое инструмента
- Не утверждай ничего о фактическом поведении системы без основания
  (лог, тест, код) — разрешено и нужно говорить "не знаю без проверки"
  вместо предположений
- Если для проверки утверждения нужен точный расчёт или подсчёт —
  выполни его явно (через код/инструмент), а не оценивай на глаз
```
